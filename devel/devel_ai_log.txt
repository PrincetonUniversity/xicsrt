2026-07-28 — F006 planning: diagnosed the large-run memory/tail problem.

Files modified:
- devel/plans/plan_F006_raytrace_memory.md (new, approved plan)
- devel/features_request.md (F006 added, Pending)

Key changes:
- Analysis/planning session only; no source files touched.

Key findings / gotchas:
- User's hypothesis (combine_raytrace is the bottleneck) is wrong: ~195 MB
  combined history at 1e6 detected rays, and with keep_history=False both
  _sort_raytrace and combine_raytrace history blocks are skipped entirely by
  their guards (xicsrt_raytrace.py:254 and :359). Neither ran in that run.
- The reported low-CPU/rising-memory tail is swap: 12 workers x ~6 GB vs
  32 GB physical. Not an XICSRT bug; will not occur on Stellar at 768 GB.
- Memory is not the 1e9-ray constraint: 195 B/ray history (65 B/ray x 3
  elements) + ~110 B/ray temporaries + ~2x transient => ~26 GB at 12 workers.
  number_of_iter=19 reaches 1e9 rays with no code change and no memory
  increase; raising time_resolution instead would multiply the peak.
- np.einsum does NOT use threaded BLAS: zero speedup 1->8 threads on the
  entire hot path ('ij,ij->i', 'ij,ijk->ik'), while a 2000^3 gemm scaled
  62->33.5 ms. 12 runs x 8 threads uses ~12 of 96 cores. User kept 12 runs.
- np.random.shuffle perturbs the global RNG stream N-dependently, so a naive
  1:1 regression test would fail on iteration 2+ after any _sort_raytrace
  change. A dedicated np.random.Generator avoids this (verified), keeping
  found rays bit-identical. Hence the Tier A (exact) / Tier B (statistical)
  harness split, and number_of_iter=3 as the divergence detector.
- Rejected the 610x rejection sampler for _sort_raytrace in favor of the 21x
  Generator.choice+flatnonzero: at 0.013% of an iteration the extra speed is
  unmeasurable and not worth the retry loop / np.unique bug surface.
- Pre-existing defects found: combine_raytrace drops 'weight' (resolves the
  jaxrt_sync.md:164 quirk when fixed); worker profiler_results are never
  returned to the parent; 'mp: gathering' times .get() on already-finished
  results and measures nothing.

Suggested follow-ups:
- Implement F006 per devel/plans/plan_F006_raytrace_memory.md (harness first).
- Out of scope, worth its own entry: per-element history compaction would cut
  history 195 -> ~65 B/ray and raise the in-flight ceiling ~3x.

2026-08-08 — Diagnosed W7-X production memory growth as a jax.jit
recompilation leak (fix lives in xicsrt_analysis, not this repo).

Files modified:
- None in this repo (read-only investigation). Fix committed separately
  in xicsrt_analysis: w7x_npablant/sources/_XicsrtPlasmaW7x.py.

Key changes:
- Investigated a report of xicsrt_train_task.py peak RSS climbing from
  3.5 GB to 8.0 GB over 100 iterations of the W7-X production config.
  Ruled out the xicsrt core engine (Dispatcher history clearing, the
  F006 fix, output_list/combine_raytrace bounding) as the cause.
- Root cause: `XicsrtPlasmaW7x.bundle_generate` (xicsrt_analysis) called
  the jax-jitted `_batched_line_params` with mask-compressed
  (`[m]`-sliced) temperature arrays. The active-bundle count `m.sum()` is
  a Monte Carlo random variable that changes almost every iteration,
  so jax.jit compiled and permanently cached a new XLA executable per
  distinct shape seen (jit's dispatch cache has no default eviction).
  Fixed by evaluating the line model on the full fixed-length
  (`bundle_count`) arrays and masking the result afterward, matching the
  existing `XicsrtPlasmaDesc._pad_masked` convention.
- Verified fix: `_batched_line_params._cache_size()` stayed at 2 for 200
  iterations post-fix vs. growing to 40 pre-fix; peak RSS plateaued at
  ~2.17 GB post-fix vs. climbing past 2.59 GB and still rising pre-fix;
  bit-exact bundle_generate output for a fixed seed before/after.

Key findings / gotchas:
- `_log_iter_diagnostics`'s "history: X GB traced -> Y GB kept" line only
  measures the ray-history dict; it does not account for JIT/device
  memory, so "0.0 GB kept" alongside rising peak RSS pointed away from
  ray history and toward something else entirely.
- `peak_rss` in that log line is `ru_maxrss`, a process-lifetime
  high-water mark — it never decreases, so its absolute value at one
  iteration is not informative; only its trend across iterations is.
- jax.jit's in-process dispatch cache is keyed on argument shape/dtype
  (not value) and is unbounded/unevicted by default; only
  `<jit_fn>.clear_cache()` frees it, which nothing in this codebase calls.
  `<jit_fn>._cache_size()` and `JAX_LOG_COMPILES=1` are useful for
  diagnosing this class of leak.
